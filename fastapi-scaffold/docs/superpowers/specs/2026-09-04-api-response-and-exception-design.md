# API 统一响应与全局异常处理设计

## 目标

为非 LLM 流式接口提供一致的成功与失败 JSON 结构，并将领域异常和框架异常集中在应用入口处理，移除路由层的重复异常转换。

## 响应契约

普通成功响应使用 `{"code": 0, "message": "success", "data": ...}`。`data` 保留原接口的业务数据：对象、列表或健康检查数据均放入该字段。

异常响应使用相同顶层字段，`data` 固定为 `null`。HTTP 状态码仍表达 HTTP 语义：认证失败 401、无权限 403、资源不存在 404、冲突 409、请求校验失败 422、未预期异常 500。业务错误码采用稳定、可读的应用级数字；框架错误使用对应 HTTP 状态码作为错误码，避免在本次引入额外错误码注册表。

`204 No Content` 继续不带响应体，避免违反 HTTP 语义。LLM 客户端调用、上游返回体和未来的流式响应均不在本次改动范围内。

## 架构

新增一个仅负责响应信封和异常处理的模块。应用入口注册四类全局 handler：领域异常、`HTTPException`、`RequestValidationError`、兜底 `Exception`。领域异常类携带其 HTTP 状态码与默认应用错误码；业务服务与认证依赖只抛领域异常。路由函数仅负责调用服务并返回业务数据。

成功响应通过应用级路由包装机制统一封装，而不是逐个路由手写包装。这样现有和新增的非流式 JSON 路由都默认遵守契约；显式 `Response`、`StreamingResponse` 和 204 响应跳过包装。

## 测试

测试覆盖成功对象、成功列表、健康检查、领域冲突、认证失败、权限拒绝、路径不存在、请求校验失败、未预期异常，以及 204 删除响应。测试断言 HTTP 状态码和统一 JSON 结构，并确认路由层不再转换领域异常。
